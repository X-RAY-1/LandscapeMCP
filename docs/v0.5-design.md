### 1.3 Foliageの現状（v0.4.0）

- **`Resolve`が全Toolで拒否する**: `Resolve`は全13 Toolが共有する対象解決で、Landscapeのどれか1つのcomponentに`AInstancedFoliageActor::HasFoliageAttached`があれば失敗します（`Attached foliage is unsupported`）。このため、Foliageが付いたLandscapeには、**read-onlyの`GetHeight`や`EvaluateWalkabilityRegion`も使えません**。v0.4の3 Toolでは`FOLIAGE_SAFETY_CONFLICT`になります。
- **Grassも拒否**: `GrassSafe`は、Landscape Grass Output、`FoliageComponents`（Grassのinstance）、grass type overrideを持つLandscapeへのApplyを拒否します。
- **他Actorの変更検出**: `CaptureCollateral`は、対象Landscape以外の全ActorをシリアライズしてCRCを取り、書き込みの前後とrollback後に一致を要求します。`AInstancedFoliageActor`も含まれるため、Foliageが動けばApplyは`ROLLED_BACK`になります。
- **Automation**: `LandscapeMCP.V04.Safety.FoliageRegression`ほか2 suiteが、Foliageが付いた状態の拒否を固定しています。

### 1.4 UE5.8のFoliage追従の仕組み（Engineソースの確認結果）

v0.5の設計の前提になるため、Engineソースを読み取り専用で確認しました。

- `FLandscapeEditDataInterface::SetHeightData`（v0.4のApplyが使用）には、Foliageを動かす引数はありません。v0.4が渡している末尾の`true,true,true`は、bounds、collision、mipの更新です。
- Foliageの追従は、Landscapeの描画・collision更新（`LandscapeEditLayers.cpp`）の中で、Project設定`ULandscapeSettings::FoliageLandscapeSnappingMode`に従って`ULandscapeHeightfieldCollisionComponent::SnapFoliageInstances`が行います。
  - `DontSnap`（**Engineの既定値**）: 追従しない
  - `SnapUnderBrushOnly`: 印を付けた範囲だけ。印はEditorのsculpt brushの経路（`FHeightmapAccessor::SetData`）が付ける。v0.4が使う`SetHeightData`で印が付くかは**未確認**
  - `SnapEverywhere`: 更新したcomponent全体
- **この追従は`GUndo`がない（Transactionの外）ときだけ実行され、Transaction中は後回しになります。** v0.4は自分のTransactionの中で更新しているため、追従が起きる場合は**Applyが返った後、Transactionの外で**起きます。その変更はApplyのUndoに含まれず、Applyの検証の後なので検出もされません。
- `SnapFoliageInstances`は、instanceを新しい地表へ移動します（`IFA->Modify()`）。**新しい着地点が見つからないinstanceは削除します。**

v0.4がFoliage付きLandscapeを一律に拒否していたのは、この「検証とUndoの外で、移動と削除が起き得る」挙動に対して正しい判断でした。v0.5はこの前提を保ったまま、安全に扱える範囲を広げます。

### 2.2 共通契約（Common Contracts）

UEとUnityは言語が違う（C++ / C#）ため、**コードの共有ではなく、契約の共有**とします。

- **Tool契約**: Tool名、入力・出力のfield、単位（ワールドcm、度）、`status`／`errorCode`の値、Dry-run既定、1回のApplyが1つのUndo単位であること。
- **意味の契約**: 傾斜の定義（実三角形、対角線00-11）、歩行可能性の分類（WALKABLE / NEAR_LIMIT / UNWALKABLE）、CreateWalkablePathのprofile計画、Foliage影響の分類。
- **適合テスト用のベクトル**: Engine非依存の入力（高さ格子、Foliageの位置）と期待値。UEのAutomationと将来のUnityのテストが同じベクトルを使う（v0.5では、UE側のPlanning / Analysisテストの入力をベクトルとして書き出す準備まで）。

Engineごとに違う部分は、Capabilityとして明示します（2.4）。

### 2.3 Engine Adapter Interface（内部C++）

```cpp
namespace LandscapeMCP::Engine
{
    struct FTerrainCapabilities { /* 2.4のfield */ };
    struct FFoliageSample   { FVector Location; double ZOffsetCm; int32 TypeIndex; EFoliageBase Base; uint32 Flags; };
    struct FFoliageInventory{ TArray<FFoliageTypeSummary> Types; TArray<FFoliageSample> Samples; TArray<FString> Unknowns; bool bTruncated; };

    class ITerrainEngineAdapter
    {
    public:
        virtual ~ITerrainEngineAdapter() = default;
        virtual FTerrainCapabilities Capabilities() const = 0;
        virtual bool ReadHeights(const FString& Path, FVector2D Min, FVector2D Max, Authoring::FHeightfieldSnapshot& Out, FString& Code, FString& Error) = 0;
        virtual bool InspectFoliage(const FString& Path, FVector2D Min, FVector2D Max, int32 MaxSamples, FFoliageInventory& Out, FString& Code, FString& Error) = 0;
        // 書き込み系（BeginOwnedEdit / WriteHeights / Commit / RollbackOwned / VerifyCollision）は
        // v0.5では宣言のみとし、既存のAuthoring::Executeを移し替えない（2.5）。
    };
    ITerrainEngineAdapter& GetActiveAdapter(); // v0.5ではFUnrealTerrainAdapterだけ
}
```

- UObjectを返さず、Engine非依存のDTO（`FHeightfieldSnapshot`、`FFoliageInventory`）だけを返します。
- 失敗は`Code`と`Error`で明示します。例外や`check`で落としません。

## 3. Phase 2: Foliage Safety

### 3.1 方針

- **既定は保護**: 既存のFoliageを動かさない、消さない、浮かせない、埋めない。
- **検出できないものは安全とみなさない**: 判定できない形式や状態は`UNKNOWN`とし、Applyを拒否します。
- **Project設定とEditor設定を変更しない**: v0.4と同じく、Toolが設定を書き換えることはしません。

### 3.2 Foliage Inspection（新Tool `InspectFoliage`）

指定した矩形について、次を返します（read-only）。

- 種類ごとの集計: Foliage Type（Asset path）、Mesh、矩形内のinstance数、付属先（下表）ごとの数
- instanceの一覧（上限付き）: 位置、回転、Scale、`ZOffset`、付属先、そのXYの地形高度、地形からの高さ（`location.z - terrainZ`）、その位置の局所傾斜
- `unknowns`: 判定できないもの（下表）
- `bTruncated`: 上限で切った場合true

| 付属先（`base`） | 意味 |
|---|---|
| `TARGET_LANDSCAPE` | 対象Landscapeのcollision componentに付属。UEの追従（snap）の対象 |
| `OTHER_COMPONENT` | 他のMesh等に付属 |
| `UNATTACHED` | 付属先なし |

| `unknowns`に入るもの | 理由 |
|---|---|
| Landscape Grass（`FoliageComponents`、Grass Output、grass type override） | Runtimeで再生成され、instance単位で追えない |
| Procedural Foliage（`UProceduralFoliageComponent`、Volume） | 再simulationで作り直される |
| Actor Foliage（`UFoliageType_Actor`） | instanceがActorで、IFAの外で動く |
| 対象Level以外のIFAが持つ範囲内のinstance（非表示・ロック中のLevelを含む。読み込まれたすべてのLevelを列挙する） | Levelをまたぐ所有関係を検証しない |
| 読み込まれていないstreaming level | 中身を検査できない |
| HISMだがIFAが所有しないinstance | Foliageとして扱わない（propとして既存のcollateral検査の対象） |

### 3.3 Foliage-aware Dry-run

v0.4の3 Tool（FlattenRectangle / FlattenPath / CreateWalkablePath）のDry-runに、Foliageへの影響を加えます。計画（量子化後の高さ）から、範囲内の各instanceについて次を予測します。

地形の高度は、Landscapeの実三角形（対角線00-11で分割、描画とChaos collisionと同じ）の重心座標補間で求めます。v0.4の読み取りToolが使うbilinear補間は、非平面のセルの中で実際の面と違うため、Foliageの評価には使いません（定義の詳細は[実装契約](v0.5-contract.md)の§4.3）。

| 分類 | 条件 |
|---|---|
| `UNCHANGED` | instanceのXYでの計画後の三角形高度の変化が量子化の半段以下で、接する三角形の傾斜の変化が0.01度以下 |
| `FLOATING` | 地形が下がる。instanceは動かないため、地表から浮く（予測量cm） |
| `BURIED` | 地形が上がる。instanceが地中へ埋まる（予測量cm） |
| `SLOPE_CHANGED` | 高さの差は小さいが、局所傾斜の変化が閾値以上 |
| `MAY_BE_MOVED_BY_ENGINE` | `TARGET_LANDSCAPE`付属で、snapping modeが`DontSnap`以外。UEがTransaction外で移動し得る |
| `MAY_BE_DELETED_BY_ENGINE` | 上と同じ条件で、新しい地表の範囲外になり得る。UEが削除し得る |
| `UNKNOWN` | 3.2の`unknowns`に当たる、または判定に必要な情報が読めない |

全体の判定（`verdict`）:

- `NO_FOLIAGE`: 影響範囲にFoliageがない
- `SAFE_TO_APPLY`: 全instanceが`UNCHANGED`
- `BLOCKED`: `FLOATING`／`BURIED`／`SLOPE_CHANGED`／`MAY_BE_*`のいずれかがある
- `UNKNOWN`: `UNKNOWN`が1つでもある

### 3.4 Safe Apply

v0.4のApplyの手順（検証 → 計画 → collision → 直前の再検証 → 1つのTransactionで書き込み → 事後検証 → rollback）に、次を加えます。

1. **Foliage gate（書き込み前）**: Dry-runと同じ評価を、書き込み直前の地形で行います。`verdict`が`NO_FOLIAGE`か`SAFE_TO_APPLY`でなければ、書き込まずに拒否します（`errorCode`はv0.4と同じ`FOLIAGE_SAFETY_CONFLICT`。詳細は`foliage`に入る）。
2. **snapping modeの確認**: 書き込むcomponentに`TARGET_LANDSCAPE`付属のinstanceがあり、modeが`DontSnap`以外なら拒否します（Transaction外の移動・削除を防ぐ）。設定は変更しません。
3. **許可範囲の固定**: 書き込みは計画の矩形（v0.4と同じ）だけ。Foliageの変更は一切許可しません（v0.5ではFoliageを書き換えるApplyはありません）。
4. **Undo / Transactionとの整合**: Foliageを書き換えないため、v0.4の「1 Apply = 1 Transaction」はそのまま保たれます。

### 3.5 Post-edit Validator

書き込み後の検証（v0.4のsource / geometry / collision / collateral）に、次を加えます。

- 範囲内の全instanceの数・位置・回転・Scaleが、書き込み前と一致すること（instance単位の比較に加え、全LevelのIFAのbyte CRCも一致すること）
- 各instanceのXYでの実際の地形高度が、Dry-runの予測と一致すること（差は`foliage.postApply.maxPredictionErrorCm`に記録する）
- 一致しなければ、v0.4と同じrollbackに進みます

### 3.6 Recovery

- **Applyの失敗時**: v0.4のrollback（自分のTransactionだけUndo）の後に、地形・collision・collateralに加えて、Foliageのinstance単位の一致を検証します。証明できなければ`ROLLBACK_FAILED`とsafety latch（v0.4と同じ）。
- **ユーザーのUndo / Redo**: Foliageを書き換えないため、Undo / Redoは地形だけを戻します。Automationで、Undo・Redoの後もFoliageが変わらないことを確認します。
- **Transaction外の遅延更新**: Applyが返った後のEditorのtickで、UEのLandscape更新が走ってもFoliageが変わらないこと（`DontSnap`）を、Automationで数frame進めて確認します。
- **中断**: Applyはgame thread上の同期処理で、途中で中断されません。Editor終了時に残る状態は、v0.4と同じくretryの記録とsafety latchだけです（メモリ上のみ、保存しない）。

### 3.7 read-only Toolの扱い

Foliageが付いたLandscapeに対して、read-onlyの解析Tool（GetHeight、GetSlope、GetHeightRegion、EvaluateWalkability、AnalyzeSlopeNeighborhood、EvaluateWalkabilityRegion）を使えるようにします。読み取りはLandscapeもFoliageも変更しないためです。円形ブラシの書き込みTool（SculptRegion、SmoothRegion、FlattenRegion）は、v0.4と同じく拒否のままにします（事後検証の仕組みがないため）。

## 4. 主なリスクと未確定事項

| 項目 | 内容 | 対応 |
|---|---|---|
| `SnapUnderBrushOnly`と`SetHeightData` | `SetHeightData`は印を付けないが、以前のbrush操作の印が残り得る（Engineソースで確認） | `DontSnap`以外は、付属Foliageがあれば拒否（Human決定R4） |
| 遅延更新の確認方法 | Applyの後、どのframeでLandscapeの更新が走るか | Apply内で明示的に更新を流して検証し、さらにAutomationで実際のEditor tickを30 frame以上・0.5秒以上進めて再確認する（`V05.Foliage.MultiFrameStable`） |
| 大量のFoliage | 範囲内に数万instance | 走査と返却に上限。上限を超えたら`UNKNOWN`（安全側）で拒否 |
| v0.4 Automationとの関係 | `FoliageRegression`等は「Foliageがあれば拒否」を固定している | v0.5の契約に合わせて期待値を更新する（理由をテストに残す） |

レビューで決めていただきたい点は、[v0.5 実装契約](v0.5-contract.md)の「8. レビューで決める点」にまとめています。
