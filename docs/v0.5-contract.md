# v0.5 実装契約

状態（2026-11-14）: **v0.5.0 Release Candidate。** Codex独立レビューの指摘（B1 / M1〜M3 / N1〜N3、§13・§13.1）を反映済み。版はHuman決定によりToolset `0.5`、Plugin `Version` 5 / `VersionName` `0.5.0`、15 Tool。設計の背景は[v0.5 設計](v0.5-design.md)にあります。

本書の区分（N3）:

- **共通のJSON / API契約**（§4〜§6）: MCP Toolの入力・出力のJSONと、判定・拒否の規則。Engineに依存しない。将来Unityを実装する場合も、同じJSONと同じ規則を満たす。
- **UE内部のC++ Adapter**（§11）: `ITerrainEngineAdapter`はPlugin内部のC++ interfaceで、MCPには公開しない。共通契約の一部ではなく、Unreal実装の構成。

## 1. 目標と完了条件

- Foliageが付いたUE5.8のLandscapeを、Foliageを壊さずに解析・編集できる
- Foliageへの影響をDry-runで予測し、Applyの結果と照合できる
- 編集後の検証と、失敗時の復旧が機能する
- v0.4の13 Toolの機能・入力schema・既存の出力fieldを保つ
- Engine Adapterの枠組みが、将来のUnity対応を妨げない
- 新しい重大なRuntime Errorがない

### 4.3 既存の3 Toolへの追加出力 `foliage`

`FLandscapeMCPTerrainOperationResult`へ、出力field `foliage`（`FLandscapeMCPFoliageImpact`）を**追加**します。既存のfieldは変えません（入力も変えません）。

| field | 内容 |
|---|---|
| `bEvaluated` | Foliageの評価を行ったか |
| `verdict` | `NO_FOLIAGE` / `SAFE_TO_APPLY` / `BLOCKED` / `UNKNOWN` |
| `snappingMode` | 評価時のProject設定 |
| `evaluation` | `DRY_RUN`（計画の予測）/ `APPLY`（このApplyの判定と事後検証）/ `RETRY_CURRENT_STATE`（書き込みのない再要求。今の地形とFoliageを今回あらためて評価したもの。`postApply`は空） |
| `inspectedCount` | 読み取り範囲（`readBounds`。`affectedBounds`と読み取りhaloを含む）内のinstance数。**走査上限を超えた場合は件数不明として`-1`** |
| `bScanLimitExceeded` | 読み取り範囲に重なる候補が走査上限を超えた。分類は不完全で、`verdict`は`UNKNOWN` |
| `unchangedCount` / `floatingCount` / `buriedCount` / `slopeChangedCount` / `mayBeMovedCount` / `mayBeDeletedCount` / `unknownCount` | 分類ごとの数 |
| `maxFloatCm` / `maxBuryCm` / `maxSlopeChangeDegrees` | 最悪値 |
| `samples[]` | 分類が`UNCHANGED`以外のinstance（上限64）：`foliageType`、`location`、`classification`、`base`（`TARGET_LANDSCAPE` / `OTHER_COMPONENT` / `UNATTACHED`）、`currentTerrainCm`、`plannedTerrainCm`、`deltaCm`、`slopeChangeDegrees`、`reason`（UNKNOWNの理由） |
| `unknowns[]` | |
| `postApply` | このApplyで書き込んだときだけ: `bChecked`、`bDeferredUpdateChecked`（Worldにfoliageがあり、transaction後に遅延更新を明示的に流して確認したか）、`bInstancesUnchanged`（読み取り範囲内のinstanceが完全一致し、**かつ全LevelのIFAがbyte単位で同じ**）、`bTerrainMatchesPrediction`、`maxPredictionErrorCm`、`verifiedCount`。retry（`RETRY_CURRENT_STATE`）では空（`bChecked = false`） |

Dry-runとApplyのどちらでも、Foliageの評価に失敗した場合は`verdict = UNKNOWN`として、Applyを拒否します。

失敗時の`stage`（診断用、`FormatFailureDiagnostic`）: 書き込み前のFoliage判定で拒否した場合は`foliageGate`、書き込み直前の再確認で拒否した場合は`preWrite`、書き込み後のFoliage検証で失敗した場合は`postFoliage`（自動rollback後）。

retry（同じ要求が検証済みの地形に対して再度来た場合）は書き込まず、記録した過去の結果の`foliage`を使いません。今の地形とFoliageを評価した結果（`evaluation = RETRY_CURRENT_STATE`）を返します。書き込みがないため、`verdict`が`BLOCKED`でも`NO_CHANGE`のまま成功します。

**地形の高度と傾斜の定義（Foliage gate、`InspectFoliage`、Applyの事後検証で共通）**

汎用の`FHeightfieldSnapshot::Sample`（bilinear補間。`GetHeight`などv0.4の読み取りToolが使う）は変えず、Foliageの評価には使いません。bilinearは、非平面のセルの中で、Landscapeが実際に描画・衝突判定する面と最大で数十cm違います（反例は§12）。

- 面: Landscapeの実三角形。各セル（頂点00, 10, 01, 11）を対角線00-11で分割し、Lower = (00, 10, 11)、Upper = (00, 01, 11)。UE5.8の描画とChaos collisionの分割と同じ（`V05.Foliage.TriangleMatchesCollision`で実collisionと照合）
- 高度: その点を含む三角形の重心座標補間
- 主三角形の選択: セル内の局所座標 fx ≥ fy ならLower、そうでなければUpper。**対角線上はLower**。高度は辺・対角線・頂点の上で連続なので、どちらの三角形でも同じ値になる
- 傾斜の変化: **その点を含むすべての三角形**（内部は1つ、辺・対角線上は2つ、頂点上は最大6つ）で、計画前後の傾斜の差の最大値
- セルの端: 格子線上の点は両側のセルの三角形を含める。Snapshotの最大辺上の点は最後のセルに属する（f = 1）
- Snapshotの端: Snapshotの外（Landscapeの中）の三角形は、Snapshot内にあるその頂点が計画前後で同じなら変化なし（書き込みはSnapshotの矩形の中だけ）。違えば判定不能（`UNKNOWN`、理由`ADJACENT_TRIANGLE_OUTSIDE_READ_BOUNDS`）。Landscapeの外には三角形がないので数えない
- Snapshotの外の点・非有限の座標: 判定不能（`TERRAIN_NOT_READABLE`）

**影響範囲の分類の閾値（固定値、入力では変えない）**

- 高さ: 計画後と現在の、上記の三角形高度の差の絶対値が`HeightQuantizationCm / 2`を**超えたら**変化あり（等しい場合は変化なし）。負なら`FLOATING`、正なら`BURIED`
- 傾斜: 上記の傾斜変化が0.01度を**超えたら**変化あり（等しい場合は変化なし）
- 判定の順: 高さ → 傾斜 → snap mode（付属かつ`DontSnap`以外なら`MAY_BE_MOVED_BY_ENGINE`）

### 5.1 対象解決

| Tool | v0.4 | v0.5 |
|---|---|---|

| `CreateLandscape` | 対象外 | 変更なし |

### 5.2 Applyの手順（追加分は★）

1. 入力検証 → 対象とEditor状態の確認 → snapshot → collateral → retry確認
2. 計画 → 書き込み前のcollision確認 → 予測collisionの確認
3. ★ Foliage gate（影響評価。`SAFE_TO_APPLY`か`NO_FOLIAGE`でなければ拒否）
4. ★ snapping modeの確認（付属instanceのあるcomponentへ書き込み、かつ`DontSnap`以外なら拒否）
5. 直前の再検証（v0.4の`STALE_PLAN`）。★Foliageを取り直し、instance・snap mode・`bSnappingSafe`・範囲のUNKNOWN・走査件数がgateの時点と同じで、かつ今の状態で再評価しても安全であること。違えば`FOLIAGE_SAFETY_CONFLICT`（stage `preWrite`、理由`FOLIAGE_STALE`）。何も書き込まない
6. 1つのTransactionで書き込み
7. 事後検証（source、geometry、collision、collateral）★Foliageのinstance単位の一致、全LevelのIFAのbyte一致、予測との照合。Foliage自体が変わった場合は、他の検証の結果より先に`FOLIAGE_SAFETY_CONFLICT`（`postFoliage`）として報告する
8. 失敗時のrollbackと復元の検証（★Foliageを含む）。証明できなければsafety latch

### 5.3 errorCode

新しい`errorCode`は追加しません。Foliageに関する拒否はすべて`FOLIAGE_SAFETY_CONFLICT`とし、`message`の先頭に次の理由コードを付けます：`FOLIAGE_IMPACT`、`FOLIAGE_UNKNOWN`、`FOLIAGE_SNAP_MODE`、`FOLIAGE_STALE`、`FOLIAGE_POST_VERIFY`。

### 13.1 円形ブラシ3 Toolの付属Foliage判定（Codex最終レビューのMAJOR、2026-11-13）

円形ブラシ3 Tool（SculptRegion / SmoothRegion / FlattenRegion）は、付属Foliageがあれば書き込まない（v0.4の契約）。v0.4.0とv0.5の途中版は、判定に`AInstancedFoliageActor::HasFoliageAttached`を使っていた。これは表示中のLevelのIFAだけを見るため、非表示・ロック中のLevelのIFAに付属instanceがあると、Dry-runもApplyも通っていた（隔離テストで再現）。

修正後は、`Resolve(Write)`と`CollectFoliage`が共通の読み取り専用helper（`TargetFoliageAttachment`）を使う。

- 対象: 読み込まれたすべてのLevel（非表示・ロック中を含む）のIFA（`LoadedFoliageActors`）
- 付属とみなす: どれかのIFAのbase cacheに、対象Landscapeのcollision componentが登録されている。instanceが使っていないstaleなIDも、v0.4と同じく付属とみなす（拒否の条件を緩めない）。逆引きmapに無くても、ID→baseの対応が対象を指していれば付属とみなす
- 付属先を証明できない（`Unresolved`）: 使用中の有効なBaseId（実instanceの`BaseId`と`ComponentHash`のkey）について、cacheのentryが無い、`BasePtr`がnull、SoftObjectPathを解決できない（読み込まれていない）、componentまたはそのOwnerが無効、のいずれか。実instanceの`BaseId`と`ComponentHash`が一致しない場合も同じ。付属と同じく拒否する（メッセージ`Attached foliage cannot be ruled out: ...`）。参照を解決するための自動ロード、Levelの表示変更、cacheの修復は行わない
- 付属なし（`None`）: 使用中の有効なBaseIdがすべて有効な別componentへ解決でき、対象へ付属していないと確認できた場合だけ
- 優先順位: `Attached` > `Unresolved` > `None`。複数のIFA・FoliageType・BaseIdがあっても、安全なinstanceを先に見たことで未解決のinstanceを見逃さない
- 読み込まれていないstreaming levelがある場合の拒否（§13）は変更なし

ErrorCode、入力・出力schema、Dry-run・Applyの契約（円形ブラシは付属Foliageがあれば両方とも拒否）は変更しない。テストは`V05.Resolve.BrushAttachedFoliageAllLevels`、`V05.Resolve.BrushStaleAndUnresolvedBase`、`V05.Resolve.UnresolvedBaseReference`。

### 13.2 円形ブラシ3 ToolのLandscape Grass判定（PR #2のレビュー、RC2、2026-11-14）

v0.3からv0.5.0 RC1まで、円形ブラシ3 ToolはLandscape Grassを検査せずに書き込んでいた（Grass Outputを持つmaterialとそのMaterial Instanceで、3 ToolのApplyが成功することを隔離Projectで再現）。GrassはUEが地形の変更後にTransactionの外で再生成するため、instance単位で保護も検証もできない。

修正後は、v0.4の3 ToolのApplyと円形ブラシが共通の読み取り専用helper（`GrassFree`）でGrassの状態を判定する。

- Grassの状態: material（Material Instanceの親、Material Function、material layerの既定の関数を含む）のLandscape Grass Output、ActorのGrass Type override、Componentのgrass type、生成済みのGrassのcomponentと非同期task。対象はActorとComponentのmaterialと、LODごとのoverride
- 判定不能として拒否: material layerを使うmaterialのMaterial Instance（layerの差し替え先を確かめないため）、editor dataのないmaterial
- 円形ブラシ: Applyで書き込む場合だけ判定し、`message`の先頭を`UNSUPPORTED_GRASS_STATE:`として拒否する。Dry-runは判定しない（v0.4の3 Toolと同じ）。変化0のApplyは従来どおり書き込まずに成功する。付属Foliageの判定（`Resolve(Write)`）が先で、付属Foliageがあれば従来どおりDry-runも拒否する
- Grassのない独自materialは、円形ブラシで編集できる（v0.3からの互換を保つ）
- v0.4の3 ToolのApply: Engineのdefault materialだけを許可する条件は変更なし。Grassの部分を共通helperへ移しただけで、拒否の集合は同じ（`UNSUPPORTED_GRASS_STATE`）

入力・出力schemaとErrorCodeは変更しない（円形ブラシの結果には`errorCode`のfieldがないため、`message`に理由を付ける）。テストは`V05.Resolve.BrushGrassState`と、既存の`V04.Safety.GrassGuardAndOuterTransaction`、`V05.Foliage.UnknownForms`。

### 13.3 Grass判定の完全性と、判定から書き込みまでの状態変化（独立レビューのMAJOR 2件、RC3、2026-11-15）

RC2の`GrassFree`は、UEの列挙API（`GetAllExpressionsInMaterialAndFunctionsOfType`）の結果が空ならGrassなしと判定していた。このAPIは解決できない参照を黙って飛ばし、入れ子のMaterial Functionの中も見ない。また、Grassの判定は書き込みの前に1回だけで、その後の`Modify()`の同期通知（`OnObjectModified`）でmaterialやGrassの状態が変わっても書き込んでいた。どちらも隔離Projectで修正前のRC2 DLLを使って再現した（[検証要約](testing.md)のRC3）。

**M1: materialのgraphの解析**

- materialとmaterial functionのgraphを、読み取りだけで最後まで辿る（`FGrassGraphWalk`）。Material Instance・Material Function Instanceは`Parent`を辿り、Function Callは`MaterialFunction`を、Material Layersは設定されたlayer・blendを辿る。expressionのpropertyにあるmaterial functionへの参照も、種類を問わず辿る（所有元へのback-pointer `UMaterialExpression::Function`だけを除く）
- 判定不能として拒否（`message`の先頭は`UNSUPPORTED_GRASS_STATE:`、本文に`cannot be inspected`と理由と対象のpath）: 親のないMaterial Instance・Function Instance、関数のないFunction Call、解析中の参照への再訪問（循環）、editor dataのないmaterial・function、未対応のclass、上限（解析中の参照の深さ64、解析済みのmaterial・function 4096、expression 262,144）の超過、material layerを使うmaterialのMaterial Instance（RC2と同じ）
- 解析済みの参照は1回だけ辿る（共有されたfunctionのDAGは循環ではない）。空のlayer・blendのslot、LODの上書きの空slotは正当なので拒否しない。ActorとComponentのmaterialは必須（UEは未設定ならdefault materialを返す）
- 解析はobjectを変更・ロード・修復しない。CastCheckedを通るaccessor（`UMaterialFunction::GetEditorOnlyData()`）は使わない

**M2: 書き込み直前・直後の再検証**

- 判定したmaterialの一覧（Actor、Component、LODごとの上書き）を記録する。`Actor->Modify()`・`Info->Modify()`は汚れ印を付けずに呼び、`SetHeightData`の直前に`GrassFree`をもう一度実行して、一覧が同じことを確かめる。違えば所有するtransactionをCancelし、何も書き込まずに拒否する（`nothing was written`）。拒否した場合、packageを汚さず、Undoの記録も残らない。Cancelはlistenerが行った変更を戻さない（このToolの変更ではないため）
- 再検証を通った後にだけ`MarkPackageDirty()`を呼ぶ（成功時の汚れ印はRC2と同じ）
- 円形ブラシ: 書き込みの後にも同じ判定を行う。状態が変わっていれば、最新のUndoの記録が自分のtransaction（GUID・context・primary object）であることを確かめてからUndoし、高さが書き込み前と一致し、Grassのinstance（component、task、grass type）がないことを確かめる。確かめられれば`rollback completed.`で拒否し、確かめられない・所有を証明できない場合は成功を返さず、そのmodule sessionの間は円形ブラシのApplyを`BRUSH_WRITES_DISABLED:`で拒否する（v0.4のApplyのlatchと同じ考え方）。Actorはこのtransactionに記録済みなので、そのtransactionの中でlistenerがActorに加えた変更もUndoで元に戻る
- v0.4の3 Tool: 書き込み直前の再検証で変わっていれば`UNSUPPORTED_GRASS_STATE`（`stage`は`transaction`）で拒否する。書き込み後は従来どおり、事後検証（`GrassSafe`を含む）とrollback・latchで扱う
- Transactionの外で起きる副作用（Grassの再生成など）は、Undoで戻るとはみなさない

入力・出力schemaとErrorCodeは変更しない。テストは`V05.Resolve.BrushMaterialGraph`（22構成、`BrushMaterialGraph.<ID>`）と`V05.Resolve.BrushGrassReentry`（3 Tool × 8構成とv0.4の`FlattenRectangle`）。automation専用のfault（`SetAutomationBrushRestoreFailure`）で、復元を確かめられない場合のlatchを確認する。
